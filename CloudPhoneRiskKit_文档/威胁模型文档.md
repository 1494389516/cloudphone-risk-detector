# CloudPhoneRiskKit 威胁模型文档

## 1. 概述

本文档描述 CloudPhoneRiskKit SDK 面对的威胁、防御措施和剩余风险。SDK 运行在潜在敌对环境中（越狱设备、注入环境、云手机平台），攻击者可能拥有 root 权限。

## 2. 威胁参与者（Threat Actors）

| 角色 | 能力 | 动机 |
|------|------|------|
| 脚本小子 | 使用现成越狱工具 | 绕过 App 限制 |
| 专业逆向工程师 | Frida/LLDB 动态分析、IDA 静态分析 | 破解风控逻辑 |
| 云手机运营商 | 定制 Android/iOS 虚拟化环境 | 批量注册/刷单 |
| 中间人攻击者 | 网络流量拦截/篡改 | 劫持远程配置 |
| 内部恶意用户 | 合法 App 用户权限 | 欺诈交易 |

## 3. 攻击面分析

### 3.1 运行时 Hook 攻击

**威胁**: 使用 Frida、Substrate、substitute 等工具 hook SDK 函数，篡改检测结果。

**防御措施**:
- **Frida 检测**: 6 个专用检测器（FridaDetector, FridaModuleDetector, FridaThreadDetector, FridaHeapDetector, FridaSocketDetector, FridaBuiltinMemorySignatureScanner）
- **Hook 检测**: HookDetector, IndirectSymbolPointerDetector, ObjCIMPDetector, PrologueBranchDetector, DyldInterposeDetector
- **运行时完整性**: RuntimeIntegrityValidator（选择器验证、指令模式、符号表一致性、栈帧验证）
- **内存完整性**: MemoryIntegrityChecker（W^X 违反、inline hook 痕迹）
- **ObjC 完整性**: IsaSwizzleDetector, ObjCSwizzleDetector, SwiftRuntimeIntegrityDetector

**剩余风险**: 内核级 hook 可绕过用户态检测。

### 3.2 调试器附加

**威胁**: 通过 LLDB/GDB 附加进程，单步跟踪检测逻辑。

**防御措施**:
- `ptrace(PT_DENY_ATTACH)` SVC 直调阻止调试器附加
- `sysctl(KERN_PROC)` 检测 P_TRACED 标志
- CSOPS 标志检查
- TTY 设备检测
- LLDBJITDetector 检测 JIT 编译痕迹
- DTraceKDebugDetector 检测 DTrace 活动
- Exception handler 注册保护
- KernelHookSideChannel 时序分析
- 硬件断点检测（`cprisk_detect_hardware_breakpoints`）
- 软件断点扫描（watchdog 24 随机文本窗口 × 1024 字节，v7.4 扩展）
- Instant-return patch 检测（watchdog `ANOMALY_INSTANT_RETURN_PATCH`）
- 信号探针（`cprisk_probe_debugger_via_signal`）
- 可疑线程枚举（`cprisk_detect_suspicious_threads`）
- Developer Disk 挂载检测

**v7.4 反调试纵深加固**:
- **Anti-dump 时序消除**: 探针间隔由固定 5s 改为 SplitMix64 驱动的 `[2, 9]s` 均匀区间 + 0–999ms sub-second 抖动，消除可被攻击者用于窗口对齐的 5s 时序神谕
- **Mach 端口基线防投毒**: 8 样本滑动最小值 CAS 校准（`CPRISK_MACH_PORT_BASELINE_CALIB_SAMPLES = 8`），校准期内不告警，防止早期观测窗口被投毒锁定高基线
- **SW BP 扫描窗口扩展**: 随机文本窗口 8→24，每窗口 768→1024 字节，降低局部 `BRK #0`/`0xFEFEFEFE` 补丁逃逸概率
- **Watchdog 启动失败可见性**: `pthread_create` 耗尽时主动设置 `STARTUP_LIVENESS | FUNCTION_PROLOGUE` 异常标志，确保 watchdog 线程创建失败不静默消失

**剩余风险**: 硬件调试器（JTAG）不可检测；内核级断点绕过用户态扫描。

### 3.3 代码签名篡改

**威胁**: 重签名 App、注入恶意 dylib、修改二进制。

**防御措施**:
- CodeSignatureValidator 验证 LC_CODE_SIGNATURE
- AppSigningIdentityDetector 签名身份验证
- DylibInjectionDetector 检测注入的 dylib
- __TEXT.__text 段哈希完整性校验
- SystemLibrarySegmentLayoutDetector 系统库布局验证
- DyldSharedCacheIntegrityDetector 共享缓存完整性
- MIEPostureDetector：仅通过 `sysctl` 读取设备级 MTE/EMTE 能力摘要（非用户内容），用于姿态分级与反篡改信号上下文；通常仅 A17 / A17 Pro 及后续较新产品线更可能暴露相关位形；不可读或非全设备具备时降级，不将“缺失”解释为“能力已开启”。

**剩余风险**: 拥有有效企业证书的攻击者可重签名。

### 3.4 远程配置劫持

**威胁**: 中间人篡改远程配置，激活 killSwitch 关闭所有防护。

**防御措施**:
- HMAC-SHA256 配置签名验证（ConfigSignatureVerifier）
- 版本回滚保护
- `localKillSwitchOverride` 本地覆盖开关
- killSwitch 激活审计日志（Logger.critical + Logger.audit）
- 证书锁定（pinnedCertificateHashes）

**剩余风险**: 签名密钥泄露后攻击者可生成合法配置。

### 3.5 云手机环境

**威胁**: 在云手机平台上运行 App，模拟真实设备。

**防御措施**:
- VPhoneHardwareProvider: GPU/BoardID/内核云手机指标
- CloudPhoneEnvironmentProvider: 网络延迟模式、屏幕分辨率异常、热状态不变性、云手机进程检测、时区不一致
- BatteryEntropyProvider: 电池电压方差分析
- HardwareCapabilityProvider: 硬件能力探测
- PhysicalSensorProbe: 物理传感器可用性
- GPURenderProbe: GPU 渲染指纹
- IMUNoiseSpectrumProvider: IMU 噪声频谱分析
- BasebandIsolationProvider: 基带隔离检测

**剩余风险**: 高端云手机平台可能完美模拟硬件特征。

### 3.6 越狱设备

**威胁**: 越狱设备上 App 的沙箱被突破。

**防御措施**:
- FileDetector: 13+ 越狱特征文件路径检测
- DyldDetector: 可疑 dylib 检测
- EnvDetector: DYLD_INSERT_LIBRARIES 等环境变量
- SysctlDetector: 系统控制参数异常
- SchemeDetector: Cydia/Sileo URL scheme
- MultiPathFileDetector: 多路径交叉验证（access/stat/open）

**剩余风险**: rootless 越狱可能隐藏部分特征。

### 3.7 Provider 注入攻击

**威胁**: 运行时替换/注入恶意 RiskSignalProvider。

**防御措施**:
- Provider 注册表封印机制（seal）
- 封印后篡改注入 `provider_tamper_attempt` 信号
- `provider_instance_replaced` 检测实例替换
- Detector 注册表同样支持封印

**剩余风险**: start() 调用前的窗口期无法检测注入。

### 3.8 重放攻击

**威胁**: 录制正常设备的风控报告并重放。

**防御措施**:
- ChallengeSession: HMAC 绑定 + 时序安全比较（timingSafeCompare）
- AppAttestSigner: Apple App Attest 签名
- ReportEnvelope: 安全信封 + nonce
- FreshnessAnchor: 新鲜度锚（Keychain 持久化）
- RiskConclusionSigner: 结论签名

**剩余风险**: 短时间窗口内的重放可能成功。

## 4. STRIDE 分析

| 威胁类型 | 场景 | 防御 | 风险等级 |
|---------|------|------|---------|
| **S**poofing | 伪造设备指纹 | 多层交叉验证、硬件探测 | 中 |
| **T**ampering | Hook/Patch SDK | 6+层检测、CFF 混淆（仅抗静态特征匹配，见 9） | 低-中 |
| **R**epudiation | 否认恶意行为 | 审计追踪（Logger.audit） | 低 |
| **I**nformation Disclosure | 逆向 SDK 逻辑 | CFF、指令替换（仅抬高静态/批量分析成本，不抗动态 trace，见 9） | 中 |
| **D**enial of Service | 大量评估请求 | RiskEvaluationActor 限流 | 低 |
| **E**levation of Privilege | killSwitch 劫持 | localKillSwitchOverride + 审计 | 低 |

## 5. 信号完整性保护

### 信号抑制检测

SDK 检测攻击者是否选择性屏蔽高风险信号：
- 跟踪前次评估的信号 ID（`previousSignalIds`）
- 高风险信号消失时注入 `signal_suppression_detected`
- 信号内容摘要（SHA-256）用于检测篡改

### 信号去重

同一 `signalOverlapGroup` 内的检测器评分取 max 而非累加，防止重复计分导致误报。

### 检测链 HMAC 证明（v7.4 新增）

`cprisk_detection_attest` 在 C 层维护一条 per-session 滚动 HMAC 链，密钥由白盒 PRF Domain 5 派生：

```
chain_0 = SHA256(label || nonce)
chain_i = SHA256(chain_{i-1} || detector_id_le4 || score_le4 || methods_sha256)
tag     = HMAC(key, label || nonce || chain_n || count_le4)
```

**防御意义**：攻击者即使 Hook Swift 层（`JailbreakEngineV2.detectV2`）将所有 score 清零，也无法同时伪造 C 层的 `attest_tag`，服务端验证 tag 时会发现不一致。单点 Swift Hook 不再足以完整绕过检测结论。

**金丝雀槽（id=0x7F）**: 每次 detectV2 结束后写入已知（score=13, method="_cprisk_canary_v1"）条目并验证，确认证明链未被截断或重放。

## 7. 已知限制

本节按**可否在工程上消除**把限制分为两类。区分的意义在于：让接入方一眼看出哪些风险只能靠服务端/纵深防御去对冲（设计层面无法补丁），哪些是当前实现层面、未来仍可继续收紧的工程缺口。

### 7.1 🔴 结构性不可修补项（设计层面无法消除，只能对冲）

这些项目源于"端侧 SDK 运行在攻击者完全可控的设备上"这一根本前提，无论投入多少工程都无法在端内单点闭合。正确做法是**承认其存在，并在服务端 / 纵深防御层面对冲**，而不是宣称已修复。

1. **内核级攻击**: 用户态 SDK 无法检测内核级 hook/patch。攻击者一旦进入内核态，所有用户态检测（含 SVC 直调、证明链、白盒 PRF）的信任根都已失守。这是用户态/内核态权限边界决定的，**不可修补**。
2. **硬件调试**: JTAG 等硬件调试器不可检测；内核级断点绕过用户态 SW BP 扫描。**不可修补**。
3. **完美模拟**: 足够精密的硬件模拟（高端云手机 / 定制虚拟化）可绕过所有软件检测。设备指纹熵在数学上不足以无歧义区分高仿环境，**不可修补**，只能靠多信号贝叶斯链抬高伪造成本。
4. **start → seal 时间窗口**: `start()` 到 `seal()` 之间存在 Provider/Detector 注入窗口。封印必须在某个时刻发生，而封印前总有一段未受保护的初始化期；该窗口可缩短但**无法消除**。
5. **根密钥可被内存转储**: Armor 根密钥（`CPRISK_ARMOR_KEY`）通过编译期环境变量注入，运行时必然以某种形式存在于进程地址空间，进程内存转储可能暴露密钥材料。白盒 PRF 仅提供**部分缓解**（root key 不可逆提取，但派生密钥/中间态在内存中仍可能被扫出）；只要代码在攻击者设备上运行，密钥材料的内存暴露面**无法在端内根除**。
6. **静态分析不可阻断（只能抬高成本）**: 二进制始终可被 IDA/Ghidra 静态分析。CFF + VMProtector + 符号剥离**增加分析难度，但不能完全阻止**——拥有足够时间与算力的逆向者最终可恢复语义。**不可修补**，定位是"提高批量化/自动化分析成本"而非"阻断分析"。

### 7.2 🟡 可缓解项（当前实现层面的工程缺口，未来可继续收紧）

这些项目不是设计层面的死局，而是当前版本实现深度/取舍的结果，后续版本仍可继续加固。

1. **start → seal 窗口缩短**: 虽然窗口无法消除（见 7.1.4），但可通过提前封印、缩短初始化链、对窗口期注入追加 `provider_tamper_attempt` 信号等手段持续**压缩可利用面**。
2. **证明链 C 层依赖**: `cprisk_detection_attest` 证明链依赖 C 层代码完整性；内核级 hook（属 7.1.1，不可修补）或白盒 PRF 被破解可绕过。但 C 层本身的完整性自检、金丝雀槽、多路交叉校验仍可继续加深，**抬高单点 Hook 绕过成本**。
3. **企业证书重签名**: 拥有有效企业证书的攻击者可重签名（见 3.3）。可通过 TeamID/bundleID/entitlement 基线漂移检测 + integrity poison 联动继续收紧识别面。
4. **rootless 越狱特征隐藏**: rootless 越狱可隐藏部分文件特征（见 3.6）。可通过 fsid 沙盒视图隔离探测、多路径交叉、bind mount 检测继续补强。
5. **配置签名密钥泄露后的合法弱配置**: 签名密钥泄露后攻击者可下发"合法但更弱"的配置（见 3.4）。安全地板（`enforceSecurityFloor`）可继续扩展强制开启的关键检测开关，缩小可降级空间。

> **诚实声明**: 7.1 各项是端侧风控的数学/权限边界，任何声称"端侧不可绕过"的表述都是营销话术。本 SDK 的真实价值在于**提高绕过成本、增加攻击者不确定性、为服务端策略提供可解释上下文**，而非端内完成最终裁决。

## 8. 安全事件响应

### killSwitch 激活

当 killSwitch 被远程激活时：
1. `Logger.critical` 记录关键日志
2. `Logger.audit` 记录审计条目
3. 如果 `localKillSwitchOverride = true`，继续正常评估
4. 建议监控 killSwitch 审计日志，异常激活立即告警

### 篡改检测

当检测到篡改时：
1. 相关 Detector 生成高分信号
2. Armor 运行时可能切换到 decoy 数据
3. 安全信封包含篡改标志
4. 建议服务端验签失败时立即阻断

## 9. 混淆/壳保护能力的真实定位（CFF / 指令替换 / VMProtector）

本节明确 `cprisk-armor` 各类代码混淆与壳保护手段的**真实威胁对抗边界**，避免读者把"增加逆向难度"误读为"抵抗动态分析"。

### 9.1 CFF（控制流平坦化 / CFFStateCodec）

**真实定位**: CFF 仅用于**反批量化分析 / 反静态特征匹配**——把顺序控制流改写成 dispatcher 驱动的状态机，使 IDA/Ghidra 的反编译输出失去直观的 if/else/loop 结构，抬高静态阅读和自动化模式匹配（如批量扫描已知检测逻辑特征）的成本。

**CFF 不抵抗的攻击**:
- ❌ **动态 trace**: 攻击者用 Frida Stalker / DBI 记录实际执行轨迹时，dispatcher 每一步跳转到哪个真实块都会被忠实记录，平坦化结构在 trace 视图下被自然"还原"。
- ❌ **调试器单步**: LLDB/GDB 单步执行会沿真实控制流前进，dispatcher 的 state 变量在寄存器/内存中可被实时观察，平坦化不构成单步障碍。
- ❌ **符号执行/去混淆器**: 针对 CFF 的通用去平坦化（如基于 dispatcher 变量的 SMT 求解、BFS 路径恢复）是公开技术，有足够投入即可半自动还原。

**结论**: CFF 是"提高静态/批量分析成本"的工具，**不是动态分析防线**。动态分析的对抗依赖反调试（ptrace/异常端口/硬件断点/watchdog）、Frida 检测、运行时完整性校验等**独立**机制，而非 CFF 本身。把 CFF 当作抗动态 trace 的手段会形成错误的安全预期。

### 9.2 指令替换（InstructionSubstitution, Pass 8）

与 CFF 同档定位：1:1 等长语义等价替换，仅打散静态指令特征、干扰基于指令序列的签名匹配，**不影响动态执行语义**，因此同样不抵抗动态 trace 与单步。

### 9.3 VMProtector（Pass 13）

将高价值函数虚拟化为自定义字节码 + 解释器。相比 CFF 对动态分析有**更高**对抗成本（攻击者需先逆向 VM 解释器与 opcode 语义，再还原字节码），但仍**不是不可破解**——VM-based 混淆的通用攻击（trace 解释器 dispatch、重建 opcode handler 语义）是成熟逆向方向。定位仍是"显著抬高逆向工时"，而非"阻断逆向"。参见 7.1.6：静态/动态分析在数学上都不可阻断，混淆手段的统一价值是**提高成本**。
